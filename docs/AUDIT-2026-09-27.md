## 1 · WHAT THE SYSTEM IS

Two applications over one PostgreSQL database (Supabase, `us-east-1`), two tenants:

- **Firm OS** (`/firm`) — 11 screens, 118 endpoints, cookie sessions, mandatory second
  factor for every member.
- **Client portal** (`/`) — 21 screens, 36 endpoints.
- **Database** — 87 tables, 297 row-level-security policies, four non-owner roles
  (`firm_api`, `portal_api`, `auditor`, `payments_service`) plus `service_role`.

Role model: the connection authenticates as `portal_api`; a firm request executes
`SET ROLE firm_api`; a client request stays on `portal_api`. Neither inherits the other.
Verified on every boot by `server/src/db/role-guard.ts`, which also enumerates every role
the connection may `SET ROLE` into and checks it is not a superuser, does not own tables,
and has no `BYPASSRLS`.

Data at the time of audit: 2 tenants, 6 staff, 4 client users, 21 matters, 30 documents,
2,391 audit events, 1 fiscal device, 7 invoices.

## 2 · WHAT IS SOUND

Recorded first because it is the larger half, and because it is unusual at this stage —
most of it is enforced by the database rather than by application convention:

1. **Tenant and matter isolation in the database.** Every policy filters on
   `kgm_tenant()` and `matter_visible()`. A client's request cannot return another
   client's row even if a service function is wrong.
2. **Client money is append-only.** `ledger_entries` refuses update and delete; balances
   are derived, never stored (`kgm_ledger_balance`, `kgm_client_trust_total`).
3. **Issued tax documents are immutable.** `guard_issued_invoice_delete`,
   `guard_issued_invoice_line_immutable` and `guard_invoice_fiscal_immutable` make an
   issued invoice undeletable and its figures frozen; the remedy is a credit note.
4. **The audit trail cannot be rewritten.** `deny_audit_mutation` and
   `assert_audit_metadata_safe`; metadata cannot carry sensitive keys.
5. **Privilege is a ring, and it is auditable.** `firm_read_matter_privilege`,
   `kgm_lawyer_ring_reason`, `privilege_releases`; every read and every refusal is
   recorded with its reason (verified: 36/36 live checks).
6. **Authentication.** scrypt with a dummy hash on every failure path (uniform timing),
   identical responses for unknown account and wrong password, per-account and per-IP
   rate limits, lockout, session tokens stored as SHA-256 fingerprints, `httpOnly`
   cookies, CSRF double-submit with a signed token, TOTP second factor with single-use
   recovery codes.
7. **Transport and headers.** HSTS with preload, `x-frame-options: DENY` in production,
   no-sniff, referrer policy, `permissions-policy`, COOP/CORP, `x-download-options: noopen`
   on GET, a CSP set on every response.
8. **Uploads.** Size, extension allowlist, declared MIME checked against the file's own
   signature, filename sanitisation, per-session upload budget.
9. **No injection.** Every statement is parameterised; the dynamic `sets.join(', ')` and
   `where.join(' and ')` fragments are built from fixed column names; no `eval`, no
   `dangerouslySetInnerHTML` anywhere in either app.
10. **Dev routes cannot ship.** `/api/dev/*` is not mounted at all when
    `NODE_ENV=production` — no flag exists to forget.

## 3 · SECURITY FINDINGS

### 3.1 · Anonymous callers could execute internal database functions — **FIXED**

**Found.** All 23 `SECURITY DEFINER` helpers in `public` were executable by the roles
`anon` and `authenticated`. `anon` holds the project's publishable key by definition and
no credential beyond it. Measured:

```
── can anon EXECUTE the SECURITY DEFINER helpers? ──
  firm_read_matter_privilege · true · true
  invoice_is_issued         · true · true
  kgm_client_trust_total    · true · true
  kgm_ledger_balance        · true · true
  kgm_next_fiscal_number    · true · true
  matter_access_level       · true · true
  matter_visible            · true · true
  kgm_lawyer_ring           · true · true
  …
```

**Exploited, as `anon`.** Any role may set an unrecognised `kgm.*` parameter, and these
helpers read session state the caller controls:

```
set_config('kgm.tenant_id', '<any tenant uuid>', true)
public.kgm_client_trust_total(…) → 65000.00      -- a real client money balance
public.kgm_ledger_balance(…)     → the balance of any ledger id
public.matter_visible(…)         → yes/no oracle over matter ids
public.kgm_lawyer_ring(…)        → the ring's answer for any member
```

`kgm_next_fiscal_number(device)` was the sharpest: it **increments** a device's invoice
counter, so a caller could have advanced the ZATCA chain.

**Mitigating fact, measured.** `anon` holds **zero** table privileges in `public`, so no
row could be read directly — the exposure was through definer functions. And one helper
held the line: `firm_read_matter_privilege` refused `anon` with
`privilege_ring_refused: matter_out_of_scope`, because it checks the caller's membership
ring instead of trusting a variable.

**Fixed — `supabase/migrations/0073`.** `revoke execute on all functions in schema public
from public, anon, authenticated`, then grant to the four application roles. Deliberately a
sweep rather than a list of names: a function added by a future migration is closed by
default. Re-verified as `anon`:

```
✗ firm_read_matter_privilege → 42501 permission denied for function
✗ kgm_lawyer_ring            → 42501 permission denied for function
✗ kgm_ledger_balance         → 42501 permission denied for function
✗ kgm_client_trust_total     → 42501 permission denied for function
✗ matter_visible             → 42501 permission denied for function
```

### 3.2 · A login role that could act as both firm and client — **FIXED**

`kgm_probe` was a `LOGIN` role with a password, a member of **both** `firm_api` and
`portal_api`, referenced nowhere in the repository. It owned nothing and held no grants of
its own — it was a key cut during construction and never collected. It could
`SET ROLE` into either audience from one credential. Dropped in `0073` (after revoking its
schema ACL, the only thing pinning it). **Its password must be treated as disclosed.**

### 3.3 · Restricting a matter silently did nothing, and the trail said it succeeded — **FIXED**

`POST /api/firm/matters/:id/restrict` answered `404 not_found` on the live system
(`firm-live.mjs`, 2 failures). Root cause, established in three steps:

1. The route's `UPDATE` matched zero rows.
2. `matter_controls` is keyed by `matter_id`, and **three of every four matters had no
   row** — 14 of 21 in the live database. Only the seeded matters had one.
3. `firm_api` holds `SELECT` on every column of `matter_controls` and `UPDATE` on exactly
   six (the restriction columns) — **and no `INSERT`**. The grant is correct: creating the
   row was meant to be the database's job, and no migration ever wrote the rule.

**Consequences.** Restricting a matter for a conflict, a client instruction or a court
order changed nothing, told the member the matter did not exist, and — because the success
audit row was written inside the transaction while the `changes === 0` test ran *after*
the commit — **recorded `MATTER_RESTRICTED, outcome: success` for a restriction that never
happened.** Meanwhile `matter_access_level()` kept answering from
`coalesce(mc.is_restricted, false)`, so the matter stayed reachable by everyone in its
practice area. An audit trail that can assert a non-event is worse than none, because it
will be believed.

**Fixed at three layers.**
- `0073` — an `AFTER INSERT` trigger on `matters` creates the control row (SECURITY
  DEFINER, because the application has no `INSERT` to do it with), plus a backfill:
  **21/21 matters now have a row**.
- `firm.routes.ts` — the refusal moved *inside* the transaction, before the audit write.
- Mirror + seeder — the SQLite trigger, and the demo seeder's richer row changed to an
  upsert so its restriction (which demonstrates §27) is not discarded.
- Regression tests: a matter created through the product must have its row and must be
  restrictable; and no success row may be written for a restriction that did not happen.

Re-verified live: `firm-live.mjs` **14 passed / 0 failed**.

### 3.4 · A drafted invoice could never be withdrawn — **FIXED (feature completed)**

An hour billed to a draft was frozen permanently. The draft could not be written off
(`issued_invoice_immutable`: needs sent / partly paid / overdue), could not be deleted (the
cascade hits the entry guard), and its hour could not be released
(`entry_already_billed`). The firm was left with a consumed number, a frozen hour, and an
unbilled total that had silently gone down with nothing on screen to explain it.

Cause: 0036's guards state "ISSUED invoice" in their messages but enforced "any invoice".
`0070` narrowed all three to the rule they state (`invoice_uuid is not null`), with a
`SECURITY DEFINER` predicate `invoice_is_issued(uuid)` because the guards run as the caller
and `invoices` is row-level-protected. `0072` grants `firm_api` UPDATE on exactly one
column of `invoice_lines` — `billing_source_key` — with a policy admitting only lines of a
non-issued invoice, so a cancelled draft can give its source keys back (otherwise the
unique index blocks re-billing the hour).

Then the product half, which did not exist: `FirmRepo.cancelInvoiceDraft`, the route
`POST /firm/billing/invoices/:id/cancel` (gated on `billing.create` — cancelling an
unapproved draft is the same act as drafting one), audit action `INVOICE_CANCELLED` (0071),
the console action with a required reason, and 9 Arabic / 9 English strings. A cancelled
draft **keeps its row, its lines and its reason** and returns its hours to `submitted` and
its expenses to `approved`.

Verified live: draft cancelled, `releasedTime: 1`, hour billable again.

### 3.5 · Support library advisories — **OPEN, MEDIUM**

`npm audit --omit=dev`: 2 moderate, 0 high, 0 critical.
`react-router` 6.30.6 — `GHSA-wrjc-x8rr-h8h6` (open redirect via backslash in `<Link>` /

### 3.6 · Operational hardening — **OPEN, LOW/MEDIUM**

- `log_connections = off`; `log_statement = ddl`. The application writes a detailed audit
  trail (2,391 events), so nothing is missing today; connection logging should be on in
  production to answer "who was in the system at 3am?".
- `ssl = on`, `password_encryption = scram-sha-256`, four storage buckets all private,
  storage objects reachable only by `service_role`.
- `kgm_roles` exist with passwords set on non-login roles (harmless, but they should have
  none) — noted for the next hardening pass.

## 4 · CORRECTNESS FINDING: THE INVOICE DOES NOT BILL THE TIME RECORD — **OPEN, HIGH**

Measured on the live database through the product's own HTTP door:

```
time entry: 95 minutes @ SAR 1,200/hour      → stored amount SAR 1,900
invoice:    quantity 1.58 × 1,200            = SAR 1,896   (VAT 284.40, total 2,180.40)
                                            → SAR 4 short of the entry
second example: 3.17 h × 1,200 = 3,804 vs entry 3,800 … and 1.58 × 2,400 = 3,792 vs 3,800
```

`(minutes / 60)` is rounded to two decimal places **before** multiplication, so any
duration that is not an exact hundredth of an hour loses a fraction of a halala — small per
line, systematic across a year, and invisible because each document is internally
consistent. The invoice and the firm's own time record disagree about the same hour, and the
invoice is the tax document.

This is a **product decision, not a bug to be patched silently**:
(a) bill the stored amount and show the hours as a description (recommended — the recorded
amount is the primary fact), or (b) keep the multiplication and require durations recorded
in an exactly convertible unit. Reported to the client for decision before any real invoice
is issued.
